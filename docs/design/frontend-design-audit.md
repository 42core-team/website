# CORE frontend design audit

This source audit covers 28 route files plus the shared root layout, their feature components, the 27 shared UI modules, the global and wiki stylesheets, and the frontend asset inventory. It includes authenticated and role-gated states represented in code. Live data, embedded applications, and authenticated screens were not exercised.

### Differences worth resolving

- **Width and rhythm.** Page containers mix Tailwind container widths and local maximums from 2xl through 7xl. Similar page types still use different heading sizes and spacing. Loading ranges from centered spinners to a layout-matched profile skeleton. Some error states appear as standalone text.
- **Local color systems.** Event phases, result pills, ranking accents, charts, and wiki callouts define color separately. The match list and a wiki notice reference warning utilities with no corresponding theme tokens in the checked-in stylesheet. Queue chart axes and bracket nodes use fixed colors, so their dark-mode appearance needs a rendered check. [Theme](../../frontend/src/styles.css) · [Event tones](../../frontend/src/components/event-status/shared.tsx) · [Match list](../../frontend/src/components/MatchesList.tsx) · [Wiki notice](<../../frontend/src/routes/wiki.$.tsx>) · [Queue chart](../../frontend/src/components/QueueMatchesChart.tsx) · [Bracket node](../../frontend/src/components/match/MatchNode.tsx)
- **Shared primitives with local variants.** The shadcn/Radix-style library already covers buttons, cards, forms, dialogs, menus, tables, and tabs. Features often override card padding, radius, elevation, or tab chrome. Event navigation changes routes, while profile and tournament tabs switch views. Each needs consistent styling within its interaction pattern. [Button](../../frontend/src/components/ui/button.tsx) · [Card](../../frontend/src/components/ui/card.tsx) · [Tabs](../../frontend/src/components/ui/tabs.tsx) · [Event navigation](../../frontend/src/components/event-status/event-header.tsx)
- **Theme controls.** The root mounts the basic navbar with ThemeSwitch. The separate Header and ThemeToggle appear unreferenced by routes and use a different token set. The root initialization script calls automatic mode “auto,” while the active provider persists “system.” [Root](../../frontend/src/routes/__root.tsx) · [Provider](../../frontend/src/lib/theme.tsx) · [Alternate header](../../frontend/src/components/Header.tsx)

## Proposed global guidelines

| Area | Guideline |
| --- | --- |
| Canvas and surfaces | Keep one theme-aware page canvas. Define a flat surface for cards, a muted surface for grouped content, and an elevated surface for overlays. Scope expressive backgrounds to media, game boards, profile art, and campaign heroes. Use image scrims and check contrast wherever content overlaps uploaded art. |
| Layout | Use one page frame with 16 px phone gutters, 24 px at medium widths, and 32 px on wide screens. Offer reading (72 characters), form (48 rem), standard (72 rem), and wide workspace (80 rem) variants. Use an immersive frame for replay and large graphs. Stack side panels on phones and keep table scrolling inside its own region. Start with 24 px between sections, 16–24 px inside panels, and 8–12 px between related controls. |
| Typography | Use one UI family with 28–36 px page titles, 20–24 px section titles, 14–16 px UI copy, and 16–18 px reading copy. Use tabular figures for timers and standings. Reserve monospace for code, logs, and IDs, and expressive display type for key titles. |
| Controls and navigation | Extend the existing primitives. Use filled primary, outline secondary, and ghost tertiary actions. Give route links a visible active state and use the shared tabs for in-page views. Standardize table heads, numeric alignment, sort indicators, and row actions. Use cards on phones when records read independently, as on Events. Keep a comparison table or a ranking view for data read across rows. |
| Semantic color and data | Map neutral, info, active/success, warning, and danger to foreground, tint, and border roles in both themes. Accompany color with a meaningful label or icon. Give match outcomes, faction colors, chart series, and podium placements their own roles. Keep phase colors, chart legends, and wiki callouts legible across backgrounds. |
| States and accessibility | Standardize loading, empty, permission, and error states. Reserve layout space during loading and show a next action where one exists. Target WCAG AA contrast, visible focus, reduced-motion support, and 44 px touch targets for major actions. Check long names, locked navigation, nested scrolling, and media at phone and desktop widths. |

## Five design directions

The [interactive drafts](design-directions.html) compare an event summary, standings table, and wiki note with the same sample content in all five directions. Each includes light and dark palettes and representative controls.

| Direction | Visual rules and application | Trade-off |
| --- | --- | --- |
| **Core Circuit** | Gray neutrals, purple actions, orange callouts, 12 px panels, and a grid scoped to the event hero. Pair the active event moment with operational facts. | Closest to the current primitives. Most of the change comes from shared tokens, page frames, and variants. |
| **Field Manual** | Warm paper, ink, forest green, serif titles, and horizontal rules. Put deadlines and event facts in a margin-like rail. Use a ruled table and wiki callouts styled like margin notes. | A good fit for long reading and onboarding. Live phases and timers need enough weight to stand out from editorial headings. |
| **Matchday** | Slate, cobalt, oversized score and time typography, sharp panel edges, and a diagonal event masthead. Treat standings like a broadcast score strip and give the wiki a quiet surface. | Strongest when tournaments are the front door. Bright accents and display type need tight limits in account and admin screens. |
| **Bot Console** | Blue-black and steel-white surfaces, teal controls, squared corners, and monospace labels. Group event facts into a telemetry strip, with a code-first visual rhythm for the wiki. | Fits queues, logs, builder, and admin. Use regular-width prose for longer docs and community pages. |
| **Guild Hall** | Plum and warm lavender, rounded panels, and a radial glow scoped to event features. Use inset cards for event facts and community identity, with soft wiki callouts. | Strongest for player and team identity. Larger radii and generous spacing work best in feature cards, leaving dense tables clear. |

## Selected direction

Core Circuit is the chosen direction. The [design guidelines](core-circuit-guidelines.md) document the palette, theme roles, layout, and shared component patterns. See the [dedicated draft](core-circuit.html) for an example.
